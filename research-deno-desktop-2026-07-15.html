Deno Desktop is not the Windows escape hatch AirNote needs.

It is a promising TypeScript desktop shell, but it does not remove AirNote’s difficult Windows work. Its default renderer is still Windows WebView2; the features that matter to AirNote—global hold-to-talk, audio capture, Unicode injection, UI Automation and local ASR—still need native Windows integration.

Verdict: do not migrate AirNote to Deno Desktop now. Confidence: 94%. Treat it as an experimental shell, not a production replacement for Electron or Tauri. Deno itself says Desktop is experimental and that platform features are still landing.

What Deno Desktop genuinely improves

For a normal React/TypeScript desktop app, it is comfortable: one Deno process serves the UI, a native window/tray API exists, and UI-to-runtime calls use in-process bindings. It can cross-compile Windows x64, macOS x64/arm64 and Linux x64/arm64 from one host.

Real benefit

Less shell plumbing

React/Vite-style UI, native windows, tray, dialogs, notifications, framework detection and a direct binding model are built in. That is friendlier than writing Tauri command wrappers for ordinary app state.

Real benefit

CEF gives renderer consistency

With CEF, Deno ships Chromium across macOS, Windows and Linux—closer to Electron’s UI behaviour than a system-webview app.

Trade-off

Default is not Electron-like

The default is WebView2 on Windows, WKWebView on macOS and WebKitGTK on Linux. That is the same “host engine differs” trade-off that Tauri already makes.

Production gap

It is not a mature Windows platform

Desktop shipped in Deno 2.9 and is explicitly experimental. That is normal for a new product, but it is the wrong timing to bet AirNote's core native path on it.

The key distinction: app shell vs. native dictation engine

AirNote is not a regular CRUD desktop app. The web UI is only the visible layer. The hard Windows work happens below it, where Deno Desktop currently does not provide purpose-built APIs.

Why this matters for AirNote

Your Windows pain is mostly privileged OS work, not Tauri UI work.

When a dictation app must see a physical key globally, capture sound reliably, inject Unicode into another process, and safely inspect an app’s focused control, every framework reaches the Windows boundary. Electron makes that boundary feel more familiar to JavaScript teams; Deno does not remove it. Rewriting the shell now risks losing working behaviour while you recreate it under a less-proven runtime.

Risk flags

Three blockers make a Deno migration the wrong production move today.

  • Experimental release: Deno says platform features are still landing.
  • Windows update gap: its own auto-updater downloads and stages patches but cannot apply them on Windows.
  • Feature mismatch: global shortcuts, foreground app injection and UI Automation are absent from the documented Desktop surface; native work would remain.

Recommendation: do not rewrite; run a bounded comparison only if needed

Recommended

Keep Tauri, isolate the Windows engine

Keep the working Rust dictation stack. Make the platform-sensitive parts explicit modules/contracts—hotkey, recording, paster, UI Automation and ASR worker—then test them on a small Windows hardware matrix. This attacks the actual failures without moving every subsystem at once.

If UI shell is the issue

Electron spike before any migration

Build a tiny Electron shell that talks to the existing Rust backend/sidecar. Do not port the hotkey, audio, typing or learning engine. Prove packaging, startup, tray, crash reporting, signing and foreground typing on real Windows machines first.

Deno use-case

Keep it as a 1–2 day curiosity spike

It is fair to prototype a settings/HUD window with CEF and call the unchanged local backend over localhost. The success criterion is developer ergonomics—not a claim that it solves native dictation. Stop if the prototype needs FFI for any core flow.

Do not do

Do not port the whole app to Deno

No Windows updater, no documented global-input API, and no established Desktop ecosystem are unacceptable for a cross-platform voice app already debugging native reliability. There is no safe rollback once the native stack is half-rewritten.

One-line decision

“Deno Desktop may someday be a pleasant TypeScript shell, but today it would move AirNote’s Windows complexity into a younger stack—not remove it.”

Revisit only after Windows updater support, documented global-input/native integration, and a sustained production track record exist.

Decision gate if we revisit later

Do not judge it by a settings screen. Pass all six on two real Windows machines: global press-and-hold with suppression; microphone capture; Unicode insertion in Chrome/Slack/Notepad; UIA edit watch; packaged MSI + signed update; recovery after a renderer/runtime crash. Until then, the migration confidence stays below the threshold for production.
