4
Formatter LLM (Step 2)
Scout 17B MoE ~150-300ms (when triggered) Regex gate
Job: Presentation formatting ONLY.
Converts spoken-form patterns to written form via JSON find/replace pairs.

Current flow:
1. needs_formatting() regex scans polished text for known spoken-form patterns
2. If regex matches → call Scout for JSON [{"find":"...","replace":"..."}]
3. Apply replacements surgically (case-insensitive find, exact replace)
4. If regex doesn't match → SKIP entirely (0ms)
Formatter input
"Anish Suman two three zero five at the rate Gmail dot com ko mail likhna hai chah baje ka."
Expected output
"anishsuman2305@gmail.com ko mail likhna hai 6 baje ka."
Actual output
"maneeshsuman2305@gmail.com ko mail likhnaa hai 4:00 PM."
↑ Wrong name (manish vs anish), wrong time (4 PM vs 6 baje), "likhnaa" double-a
PROBLEM 1 — Regex gate too narrow:
• "chah baje" not caught (regex has "chheh" not "chah/cheh/chhah")
• "paanch sau" not caught (regex missing "sau")
• Hindi number transliterations vary wildly: chheh/chah/cheh/che

PROBLEM 2 — Regex is the wrong approach:
• The LLM is smart enough to recognize "chah baje = 6 o'clock" without regex help
• But the regex GATE prevents the LLM from seeing the text
• We're using a dumb filter to decide when a smart model should run

PROBLEM 3 — LLM formatting errors:
• "छह baje" (6 o'clock) → "4:00 PM" (wrong number entirely)
• Name spelling inconsistent across recordings
• The LLM sometimes changes content words it shouldn't
DECISION NEEDED:

Option A: Remove the regex gate entirely. Run formatter on EVERY recording.
Cost: +200ms per recording. Benefit: catches everything the LLM can see.

Option B: Keep regex gate but make it much broader (catch any Hindi number word).
Cost: more false triggers. Benefit: still skips pure-English recordings.

Option C: Hybrid — run the formatter only when the polish step outputs Hinglish (detected by checking for romanized Hindi words). English-only recordings skip.
