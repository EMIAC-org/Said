TL;DR

Recommendation: make DeepSeek the proposal engine, not the final approver. The user's card approval is the write gate for learned vocabulary and active aliases.

1. DeepSeek notices

It receives transcript, AirNote output, user-kept text, edit spans, app, model, and profile context. It returns candidate swaps and profile updates.

2. User approves

The status card shows exactly what would be remembered. Nothing becomes active vocabulary until the user chooses Learn.

3. Safe alias pass

After approval, DeepSeek generates possible STT aliases for the approved term. Rust blocks common Hinglish/English sources before activation.

Rules that must be enforced

These are the non-negotiables for the DeepSeek prompts and Rust validators.

Layer Rule Why
Proposal prompt DeepSeek proposes swaps only from visible edit evidence. Prevents profile hallucinations.
Proposal prompt Never propose common Hinglish/Hindi/English words as alias sources. Stops errors like kaam -> Kafka.
User card User approves specific memory items, not an invisible profile patch. Makes learning understandable and reversible.
Alias prompt After approval, generate possible STT aliases only for the approved canonical term. Decouples term learning from alias expansion.
Rust validator Common source, dictionary/common Hinglish, intent-change, and long phrase gates still block. DeepSeek is not trusted as final authority.
Runtime Only active approved aliases affect dictation; candidate aliases are display-only. Keeps runtime stable.

Implementation waves from here

Smallest sane sequence to turn the current autonomous updater into HITL.

Wave A: server proposal model

  • Change `learn-from-edit` terminal result from direct profile apply to `pending_review` proposal.
  • Store `proposed_terms`, `proposed_swaps`, blocked proposals, and reason in audit/job table.
  • Add approve/reject endpoints for profile proposals.

Wave B: HITL card

  • Control-plane notifies desktop when proposals are ready.
  • Status card shows source -> canonical, reason, and safety labels.
  • Approve creates canonical term; reject stores negative/blocked signal.

Wave C: safe alias generation

  • After approval, second DeepSeek prompt generates aliases for approved canonical term.
  • Rust validator blocks common words and unsafe aliases.
  • Aliases are candidate first, active after approval/evidence.

Wave D: Vocabulary page

  • Desktop reads profile memory from control-plane.
  • Show pending, active terms, aliases, profile context, blocked sources, and audit.
  • Keep local SQLite vocabulary as legacy/read-only until migration is done.
Expected decision: approve this HITL shape first. Then implementation should pause autonomous apply mode and make pending review the default outcome for user-visible learning.
