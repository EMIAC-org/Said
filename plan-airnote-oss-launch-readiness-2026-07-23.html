AirNote / launch plan
Project roadmap · 23 July 2026 · Abhishek Verma

Open-source launch readiness before monetisation.

Defer subscription logic. Ship a simple local-first configuration experience, make AirNote’s data boundary real in code, restore learning as a local-only feature, then remove the legacy paths that contradict the product.

Decision under review

What to build first

Sequence the release around user trust and reliable first-use—not provider breadth or billing.

Recommendation — proceed

Launch with content-free AirNote telemetry, explicit local retention, and a small catalogue of routes proven end to end.

Confidence: 88%

The codebase already has strong local models, a real wizard, metadata telemetry, and edit-watch safeguards. The data boundary is the missing prerequisite.

Do not claim “no data”

Cloud STT/polish still processes data at the selected provider. The honest promise is: AirNote does not retain or upload dictation content.

Five small waves

Ship the irreversible work first.

Click a wave for its exit criteria. No subscription, payment, or entitlement work belongs in these waves.

Wave 0 — privacy contract & regression fence

  • Write a one-page policy: never upload or retain in AirNote cloud transcripts, polished output, edit text, audio, focus-field snippets, or free-form traces.
  • Define what may remain: coarse usage, model/version/platform, latency, success/error code, duration bucket, and aggregate edit outcome.
  • Choose local policy: local history/learning is opt-in or explicit retention; audio is deleted after terminal processing by default.
  • Add payload tests that fail on forbidden keys/known text in every outbound dictation request, queued outbox replay, diagnostics, and Sentry context.

Wave 1 — remote privacy cutover

  • Replace dictation observability payloads with a narrow metrics-v2 contract; do not overload the existing text-bearing DTO.
  • Stop upload and control-plane persistence of raw/polished/final text, aliases, trace JSON, app name, device/run identifiers, and content flags.
  • On upgrade, delete or quarantine queued plaintext outbox records so old unsent data cannot upload later.
  • Make the server reject old text-bearing endpoints/fields; remove remote run detail/history views before relying on desktop changes.
  • Inventory and purge historic cloud text after backup/retention decision; document provider processing separately.

Wave 2 — simple, truthful first run

  • Start supported Macs with “Recommended local” and a clear download; make account connection optional for local use.
  • Put one short model decision in onboarding: Local / cloud provider with own key / advanced catalogue. Keep the real dictate-to-test step.
  • Use one capability registry for onboarding, Settings, migration notices, and docs—no hardcoded “Cloud Whisper” copy.
  • Make each route show: offline/network, audio destination, key owner, storage size, language focus, and readiness error.
  • Do not surface a provider until credential storage, key test, fallback, and removal flow are working.

Wave 3 — edit watcher, local only

  • Extract the large watcher from Tauri main into capture, ownership, timing, classifier, and local-learning modules.
  • Keep PID/field fingerprint/owned-span/generation cancellation safeguards; they prevent learning from unrelated edits.
  • Turn watcher logs into codes and counters—never snippets—and make learning write locally only.
  • Add fixtures for capture → diff → classification → local save, plus a hard network assertion that no text is uploaded.
  • Pick one review path after one release cycle: pending edits or review sessions, not both.

Wave 4 — catalogue, cleanup & launch gate

  • Publish a single catalogue schema: stage, local/cloud/BYOK, OS support, download size, language fit, privacy, provider, key, health, stable/beta.
  • Ship only tested routes: current local speech models plus validated BYOK adapters. Meetings must declare their own data/model route.
  • Remove dead UI only after confirmed non-use; migrate/remove legacy provider preference columns and hardcoded display paths deliberately.
  • Open-source launch pack: threat model, privacy/data map, telemetry toggle, local-data deletion, reproducible build guide, security reporting, contribution guide.
  • Freeze scope and run the fresh-install/no-account/offline/invalid-key/upgrade test matrix before Product Hunt.
Boundaries

What belongs in this launch

In scope

  • Dictation privacy: no AirNote cloud retention/upload of content.
  • Useful telemetry: minimized, aggregate, transparent, and controllable.
  • Local learning: user-controlled text retention and deletion.
  • Onboarding: optional sign-in and a simple, route-aware catalogue.
  • Reliability: make edit watcher testable before expanding it.

Explicitly deferred

  • Subscriptions: payment, entitlement, quotas, billing portal.
  • Provider breadth: aspirational models without tested adapters.
  • Cloud Meetings promise: it remains a separate consent/data boundary.
  • Large refactor: no blanket deletion of history/learning until policy and dependencies are proven.
Architecture cross-check

Two viable privacy choices

The choice changes how much edit-learning value survives.

Recommended: local-only content

Retain history and learning locally under a visible user setting. Cloud receives only minimized metrics. This preserves edit watcher utility and supports a credible privacy story.

Alternative: fully ephemeral dictation

Store no content locally by default. Simpler privacy posture, but history, personal correction learning, review, and recovery become unavailable or must be rebuilt differently.

Rejected: “remove one uploader”

Text currently exits through observability, runtime history, edit traces, diagnostics, and existing outbox rows. A partial removal creates a false privacy claim.

Risks & gates

Things to resolve before launch

Old clientsOlder desktop versions can continue sending content. Mitigation: server rejects text-bearing payloads before public privacy claims.
Cloud routingBundled keys are not BYOK and cloud providers process audio/text. Mitigation: disclose route-specific processing; move keys to OS keychain only when BYOK is actually shipped.
DiagnosticsFree-form error/trace context can include content. Mitigation: remote diagnostics use allowlisted scalar fields and error codes, or remain opt-in/off.
MeetingsCloud meetings intentionally persist transcript chunks/summaries today. Mitigation: separate consent/feature boundary; do not imply dictation policy covers Meetings.
CleanupHistory, Insights, export, and profile features depend on text. Mitigation: map dependencies and preserve only intentional local functionality before migrations.
