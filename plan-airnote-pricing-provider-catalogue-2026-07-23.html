Decision plan · July 23, 2026 · Owner: Abhishek / AirNote

AirNote becomes local first, BYOK-capable, and paid without pretending cloud is free.

A three-lane product: private local models for everyone, bring-your-own-key control for power users, and a managed subscription for people who want the best result with no provider setup.

Recommendation

Launch Free Local + BYOK, Pro at $8, and Max at $10 with a hard high-accuracy allowance.

Make the provider catalogue a product layer, not a pile of switches. The same explicit profile must drive dictation and Meetings, with only validated providers visible in the client.

01Free is useful: local STT and local polish stay first-class, never a crippled trial.
02BYOK is honest: users choose and fund OpenAI/OpenRouter-compatible providers themselves.
03Max is bounded: ₹40/hour Sarvam usage cannot be unlimited at $10/month.
This is a commercial and architecture draft. Provider names, model weights, prices, and included hours are marked as decisions until verified in the catalogue work.

What is decided, and what is not

This is a combined product decision and system plan. It is designed to leave us with one coherent menu—not a settings screen full of provider-specific logic.

Decided direction

Choice belongs to the user

AirNote will support local models, user-managed API keys, and managed AI. Privacy, price, and quality are deliberate trade-offs a user can understand.

Decided direction

Meetings share the same engine

Meetings must run through a selected audio/transcription/polish profile—not quietly use a separate cloud stack.

Open decision

Exact catalogue & allowance

Confirm which models are distributable on macOS/Windows, their quality lanes, license, download size, price, concurrency, and the Max usage allowance.

Important distinction: Cerebras is a fast LLM inference option for polish/knowledge work. It is not a substitute for STT. Every managed plan must state both its transcription provider and its polish provider.

Proposed product offer

Recommend $8 rather than $5 for the managed tier. The free local/BYOK option protects price-sensitive users; Pro needs room for support, payment fees, retries, and reliable hosted capacity.

Max

Best accuracy + context

$10 / month

Premium speech quality, knowledge-aware polish, and priority execution—but explicitly metered high-cost audio.

Do not market Max as unlimited. At the supplied ₹40/hour Sarvam cost, 10 hours cost ₹400; 20 hours cost ₹800. A $10 plan only stays healthy if Max has a visible allowance and a safe post-allowance policy.

One selection model for every mode

A profile is the one thing a user chooses. It contains STT, polish, privacy, runtime, cost behavior, and whether Meetings can use it.

01 — Capture is provider-agnostic

Keep the hotkey, audio capture, transcript preview, and final paste independent from the model. The audio route should receive a profile ID, not a provider-specific switch.

run(mode: Dictation | Meeting, profile_id, audio) → Result<RunOutput, UserSafeError>

02 — Profiles are the UX boundary

Each profile declares its privacy, provider chain, availability, expected speed, cost owner, fallback order, and whether Meetings are permitted. The UI shows profiles; it should not expose raw endpoint options by default.

profile = { kind, stt_chain, polish_chain, key_owner, meeting_capability, allowance_policy }

03 — STT adapters own reliability

Every STT integration needs a normalized audio contract, a preflight check, typed errors, cancellation, observability, and a verified model/region. Provider-specific retries must not leak into the desktop UI.

SttProvider::transcribe(audio, language_hint, cancellation) → Transcript + Usage

04 — Polish adapters preserve one prompt contract

Number formatting, Hinglish behavior, personal knowledge context, and streaming semantics must remain equivalent across local, OpenRouter BYOK, and managed Cerebras. The provider changes; the product behavior does not.

PolishProvider::stream(transcript, profile, context) → token stream + Usage

05 — One ledger, one explanation

Record what ran, on whose key, how much allowance it used, and what the fallback was. Let a user see “Max allowance used 02:18 of 10:00” before it becomes a support ticket.

UsageLedger::record(profile, provider, seconds, tokens, billed_to)

Catalogue entries are server-validated capability records. The app receives only safe, compatible choices—not URLs, magic headers, or hidden assumptions.

Non-negotiable definition of done

A provider is not “supported” until it passes all of this.

  1. Preflight and model discovery. Validate key, model name, audio format, region, and account capability before it appears enabled.
  2. Canonical benchmark. Run English, Hindi, Hinglish, names, numbers, silence, and long-form audio—not just a happy-path clip.
  3. Typed failure contract. Timeouts, quota, malformed audio, auth failures, and provider outage map to useful AirNote actions.
  4. Usage contract. Record seconds/tokens, ownership (user vs AirNote), allowance impact, and provider request ID where permitted.
  5. Fallback contract. A profile declares exactly what happens when a provider fails; never silently fall back to a paid route.
  6. Release gate. macOS and Windows tests, cold start, model download/recovery, and real provider smoke tests are green.

Decision rule

$10 can work with a cap; it cannot safely be unlimited.

At the starting 10-hour allowance, provider cost is ₹400 / roughly $4.55 at the plan’s sample exchange-rate assumption. That leaves roughly $5.45 before every other business cost.

Do not raise the included allowance until we have measured real use and verified Sarvam’s effective production pricing, retries, and concurrency. Add-on hours or a local/BYOK fallback are the honest release valve.

Recommended initial entitlement: 10 hours of Max STT per billing month, with an in-app meter and a confirmation before a Meeting consumes remaining Max hours.

Meetings are a profile consumer—not a fourth product

Meetings make usage spiky and can consume hours quickly. They cannot bypass cost, privacy, or provider policy just because they are a different screen.

What works

Any profile that declares Meeting support

  • Local profile: process audio locally where hardware supports it.
  • BYOK profile: use the owner’s configured provider and show that their key will be used.
  • Pro / Max: use managed capacity and charge usage to the plan allowance.
  • Persist the exact profile/provider used with the meeting record for audit and support.
Guardrails

Meeting-specific policy

  • Show estimated allowance impact before cloud recording begins.
  • Switching profile mid-meeting should make a new, explicit segment.
  • When allowance ends, stop or switch only to a pre-approved local/BYOK profile—never surprise-bill.
  • Knowledge-base context is opt-in and visibly scoped per meeting.

Risks and open questions

These are release blockers, not things to hide behind a “beta” label.

1

Local model licensing and distribution

We need explicit redistribution rights, model-card limits, source checksums, and platform support before a model gets a size slot in the product.

2

Provider reliability and concurrency

“API works once” is insufficient. Measure cold start, sustained parallel calls, error rates, and cancellation behavior for each managed route.

3

Knowledge-base privacy

Clarify where context is stored, what leaves the device, whether it is sent to a BYOK provider, and whether it is applied to Meetings.

4

Max allowance accuracy

Verify Sarvam’s real effective INR cost, any minimums, taxes, retry billing, and rate limits. The 10-hour cap is a planning position, not a final margin model.

5

Existing provider debt

Current models and routes must be retired or migrated cleanly. The client should not retain stale provider names, hidden switches, or multiple policy implementations.

6

Entitlements before billing

Build usage enforcement, grace handling, and a support override path before turning on recurring payments. Otherwise a billing issue becomes an access issue.

Immediate next steps

Sequence matters: provider selection is an evidence problem before it is a UI problem.

  1. Approve the tier promise. Decide whether $8 / $10 / 10 Max hours is the launch contract, and explicitly name Pro’s managed STT allowance.
  2. Write the catalogue schema. Capture model ID, provider, platform, size, license, languages, streaming/meeting capability, cost owner, health, fallback, and tests.
  3. Make the benchmark suite. Use real English, Hindi, Hinglish, names, number, and noise samples with latency/concurrency measurements.
  4. Run a provider round. Validate each local class, Parakeet, OpenAI STT BYOK, OpenRouter Gemma BYOK, Cerebras polish, and Sarvam Max against the same contract.
  5. Only then design settings. Settings should render profiles and catalogue capabilities—not contain product rules.
