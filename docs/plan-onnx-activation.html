ONNX Model Activation Plan v2.2

Flipping the neural scorer from shadow-only to live corrections.
Every edge case. Every learning signal. Every safety gate.

1. Where We Are Right Now

ONNX Neural Scorer
SHADOW-ONLY — zero corrections applied
The model runs on every dictation. It scores every suspicious token against every vocab candidate. It logs the result. It never applies a single correction. All live corrections come from exact STT alias match, edit-policy rules, and cluster-fuzzy pass.

Current Correction Pipeline (4 passes)

Pass 1
Exact Alias
STT heard "airnot" → exact match in stt_replacements → "AirNote"
Pass 2
Edit Policy
Context-aware rules from user edits. Multi-token. Active if 2+ confirmations.
Pass 3
Cluster Fuzzy
High-similarity match against edit-policy targets. Threshold: 0.78
Pass 4
ONNX Neural
Scores all remaining tokens. Logs. Never applies.
The one-line change

In tier2.rs, the fuzzy_shadow_only_skipping() function calls apply_tier2(..., false).

That false is allow_apply. Change to true and the model starts making live corrections.

But we can't just flip it. The training data has quality issues that would cause false positives.

2. Why We Can't Just Flip The Switch

Training Data Quality Gaps

GAP 1
Real English AND Hindi words as aliases
If user says "air note" and corrects to "AirNote", the system creates alias air note → AirNote. "air" is a real English word. "bol" is a real Hindi word. If the model trains on either as a positive, it will aggressively replace them in all speech.

English: COMMON_WORDS has ~70 words. Misses thousands: "air", "note", "sprint", "dock", "tower", "graph".
Hindi: Only 6 Hindi words in the filter. Misses critical Hinglish words like "bol", "bas", "kya", "dekh", "sun", "chal", "mil" — all commonly emitted by Local speech in Hinglish mode.

Rare Hindi is fine: Words like "pratigya", "vimarsh", "anushasan" are safe as aliases because they almost never appear in casual Hinglish dictation. Only high-frequency conversational Hindi needs blocking.
GAP 2
Proactive distortions generating real words
generate_proactive_distortions("sprint") creates char deletions like "print", "sprit". vowel_substitutions("node") creates "nod", "ned". These are real English words — if they become training positives, the model will aggressively replace "print" with "Sprint" everywhere.

Current check: is_safe_distortion() only checks common words + length. Doesn't check the dictionary.
GAP 3
Single-token splitting of compound terms
"AirNote" as a compound should match "air note" (two tokens), but the ONNX model only handles single token → single candidate scoring. It can't reason about "air" + "note" together.

Multi-token compounds need a different handling strategy — edit-policy rules or dedicated compound matching.
GAP 4
No empty/junk transcript filtering
Local speech sometimes returns empty strings, single characters, or garbled fragments. If these get stored as correction pairs ("" → "AirNote"), they pollute training data.

Current check: len(token) < 3 filter exists but doesn't catch semantic junk.
GAP 5
Case variants treated as separate aliases
"Airnote", "airnote", "AIRNOTE", "AirNote" — these all get stored as separate aliases pointing to the same canonical form. This inflates alias_count and creates noisy features.

The normalize function lowercases, but the training script creates variants from the original case forms.
GAP 6
Cross-term confusion in small vocab
With 5 vocab terms, the model has few candidates — fine. But if two terms are similar ("Marcos" and "Macobs"), the model needs very clear training signal to distinguish them. Currently, both would get positive examples from similar distortions.

Compound Word Handling (the "air note" → "AirNote" problem)

Two separate mechanisms, not one
  • CamelCase splits → Edit-policy rules (multi-token): "air note" as two tokens gets handled by edit-policy bigram matching. When user corrects "air note" to "AirNote", we record a 2-token edit-policy rule (air, note) → AirNote. This already works in Pass 2.
  • Joined form → STT alias (single-token): "airnote" as one smushed token goes through the ONNX scorer as a valid alias for "AirNote". This is safe because "airnote" is NOT a real word.
  • "air" alone → REJECTED: Never create a single-token alias "air" → "AirNote". Gate G1 catches this. The word "air" exists in the dictionary.
  • "note" alone → REJECTED: Same reason. "note" is a real English word.

B. Learning Scenarios — Every User Action

✅
User KEPT the output
Signal: Positive for all Tier2 corrections applied
Action: tier2_policy::reward_mapping() +0.5
Exact alias gets use_count++, weight bump
Edit-policy rule gets positive_count++
ONNX learn: Next retrain picks up higher policy_weight
✏️
User REPLACED a word
Single change: Classify route processes immediately
Multi-change: Review card shown, user picks
ONNX learn:
  • Replaced word becomes new alias (if not a dictionary word)
  • Replaced word → edit-policy rule with context
  • Proactive distortions generated (with dictionary gate)
  • Retrain fires after 5s debounce
👎
User REVERTED a correction
Signal: Strong negative
Action:
  • tier2_policy::penalize_mapping() -0.75
  • Delete the specific wrong STT alias
  • DO NOT delete the vocabulary entry
  • Edit-policy rule gets negative_count++
  • If negative_count ≥ 2 → rule blocked
ONNX learn: Next retrain sees negative policy weight → excluded from positives
🚫
User did NOTHING (no edit at all)
Signal: Weak positive (user accepted output implicitly)
Action:
  • Reward active tier2 decisions: kept_unrewarded → +0.15
  • Active vocab terms get use_count++
ONNX learn: Gradual weight increase from usage, tiny policy boost
➕
User ADDED a new word (not in transcript)
Detection: Word in user_kept but not in ai_output and not in transcript
Question: Did Local speech drop it?
If yes (word is a known vocab term):
  • Star the term → add to Local speech keyterm bias
  • User explicitly chose to type this word Local speech missed
If no (completely new word): Not learnable from a single insertion; no context
🔄
Retrain fires (5s debounce)
Trigger: Any learning event + no review card pending
Mode: Micro (15 epochs, ~2s)
What changes:
  • New aliases become positive examples
  • Negative policy weights become negative examples
  • Dictionary hard negatives regenerated (or cached <1h)
  • ONNX artifact hot-reloaded on next dictation

C. Edge Cases — Things That Can Go Wrong

EDGE
Local speech returns empty response
User speaks but STT returns ""
Gate: len(token) < 3 filter + is_suspicious_token() rejects empty/short tokens
Training: No alias created for empty transcript_form (upsert rejects empty)
Result: Safe. No corruption.
EDGE
Local speech drops word entirely
User says "AirNote is great" → STT: "is great"
ONNX can't help — there's no token to score against.
Solution: If user adds "AirNote" back, and it's already in vocab, star it for Local speech keyterm bias. This is the only mechanism that helps with dropped words.
EDGE
"air" + "note" spelled as two words
STT: "let's open air note"
ONNX (single-token): "air" → skipped (dictionary word, not a candidate)
Edit-policy (multi-token): (air, note) bigram → "AirNote" ✓
Key: Compound correction handled by Pass 2, not Pass 4. ONNX only does single tokens.
EDGE
AirNote pronounced as one word "airnote"
STT: "let's open airnote" (smushed together)
Pass 1: Exact alias "airnote" → "AirNote" ✓
If no alias yet, Pass 4 (ONNX): "airnote" vs AirNote → high edit_sim + phonetic_sim → APPLY
Safe: "airnote" is not a real word, so no false positive risk
EDGE
Two similar vocab terms: "Macobs" vs "Marcos"
Token: "marcos"
Score vs Macobs: 0.72 (edit_sim moderate)
Score vs Marcos: 0.95 (near-exact)
Margin = 0.23 ≥ 0.18 → Marcos wins clearly
Safe: Margin threshold prevents ambiguous corrections
EDGE
Proactive distortion "spint" from "Sprint"
char_deletions("Sprint") → "Spint", "Srint", "Sprit", "Sprnt", "Sprin"
Gate G1: Is "sprit" a dictionary word? Yes → REJECTED
Is "spint" a dictionary word? No → KEPT as valid distortion
Safe: Dictionary filter catches the dangerous ones
DANGER
Model replaces a real word with vocab term
User says "I want to sprint to the finish"
If "Sprint" (brand) is in vocab, could model replace "sprint" → "Sprint"?

Protection layers:
  1. is_suspicious_token("sprint") → false (it's a known English word) → SKIPPED
  2. Even if checked: "sprint" IS a dictionary word, gets is_dictionary_word=1.0 feature → model penalizes
  3. Score threshold 0.86 + margin 0.18 → unlikely to pass for a common word
DANGER
Hindi word sounds like a brand
User says "yeh amaze kar diya" (this amazed me)
"EMIAC" is in vocab. Phonetic sim("amaze", "emiac") = moderate

Protection:
  1. "amaze" is a dictionary word → is_suspicious_token() returns false → SKIPPED
  2. Edit sim only 0.4 → well below 0.86 threshold
DANGER
Common Hindi verb matches a vocab distortion
User says "mujhe bol diya usne" (he told me)
"Bolt" is in vocab. edit_sim("bol", "bolt") = 0.75, phonetic_sim = 0.80

Without Hindi gate: "bol" is NOT in /usr/share/dict/words (English dict). is_suspicious_token("bol") returns true. Model might score "bol" → "Bolt" at 0.87 → FALSE POSITIVE

With Hindi gate (G1): "bol" is in HINDI_COMMON_WORDS → is_common_any_language("bol") = true → is_suspicious_token() returns false → SKIPPED

This is exactly why the English dictionary alone is not enough. Hindi common words are invisible to /usr/share/dict/words but appear constantly in Hinglish dictation.
NORMAL
Rare Hindi word IS a valid alias
Vocab term: "Vimarsh" (a brand/product name)
STT distortion: "vimarash" → alias for "Vimarsh"

"vimarash" is NOT in English dict, NOT in Hindi common words (it's a rare literary word).
is_common_any_language("vimarash") = false → ALLOWED as training positive

Rare Hindi words are safe because they almost never appear in casual speech. If Local speech emits "vimarash", it's very likely the user meant "Vimarsh".

5. Implementation Plan — What Changes Where

Phase 1: Harden Training Data REQUIRED
Fix the quality gates BEFORE enabling the model.

File Change
train_correction_model.py Unified common word filter (English + Hindi):
• English: Use /usr/share/dict/words (already loaded!) as a full negative gate. Any alias that IS a dictionary word → skip as positive, add as negative instead.
• Hindi/Hinglish (~120 words): Add a HINDI_COMMON_WORDS set covering everyday conversational romanized Hindi. These are words Local speech routinely emits in Hinglish mode. Rare/literary Hindi is fine as aliases — only high-frequency words are blocked.
• Combined into one is_common_any_language(token) function used everywhere.

Cross-term collision gate: Before adding a positive, check if the alias is closer (by edit_similarity) to a DIFFERENT vocab term than its target. If yes → skip.

Minimum edit distance: Positive alias must have edit_similarity ≤ 0.90 with its target (too-easy pairs add no learning signal) AND ≥ 0.30 (too-far pairs are noise).
stt_replacements.rs Upgrade is_safe_distortion(): Use the same unified is_common_any_language() check — English dictionary + Hindi common words. Reject any proactive distortion that is a real word in either language.
stt_replacements.rs Alias insertion guard: In upsert(), reject if transcript_form (after normalization) is a common word in any language (English dict OR Hindi common) AND the correct_form is not the same word (case-insensitive). This prevents "air" → "AirNote" and "bol" → "Bolt" from ever entering the table.
Phase 2: Strengthen Runtime Safety REQUIRED
Make the scoring engine conservative enough for live corrections.

File Change
tier2.rs Upgrade is_suspicious_token(): Currently checks if token is in a small hardcoded list. Expand to use is_common_any_language() — English dictionary + Hindi common words. Any token that IS a known word in either language should NOT be scored by the ONNX model.

This is the single most important runtime gate. It prevents the model from touching "bol", "bas", "air", "sprint" — words that are real in English or Hindi but might phonetically resemble a vocab term.

Exception: If the token has an exact STT alias or active edit-policy rule, it gets corrected by earlier passes (1-3) regardless. The ONNX model (Pass 4) only handles tokens that aren't known words and weren't caught by earlier passes.
tier2.rs Confidence logging: When ONNX applies a correction, log it distinctly: [tier2] ONNX-LIVE: "knot" → "AirNote" score=0.91 margin=0.23
This makes it easy to audit what the model is doing in production.
tier2.rs Max replacements per recording: Already capped at 3. Keep this. With ONNX live, the cap becomes a safety net — even if 4 tokens score high, only 3 get replaced. Protects against catastrophic model failure.
Phase 3: Flip the Switch THE CHANGE
Enable live corrections from the ONNX model.

// tier2.rs — fuzzy_shadow_only_skipping() // Currently: apply_tier2(transcript, &candidates, Some(&model), protected_tokens, &self.policy_weights, false) // After: apply_tier2(transcript, &candidates, Some(&model), protected_tokens, &self.policy_weights, true) // Also rename the function: fn fuzzy_shadow_only_skipping → fn fuzzy_scoring_pass

That's it. One boolean. But only safe because Phase 1 and 2 are in place.

Phase 4: Close the Feedback Loop LEARNING
ONNX corrections participate in the same feedback system as all other corrections.

User Action What Happens to ONNX Correction
User keeps the text (no edit) tier2_decision_events.reward_outcome = 'kept_unrewarded' → +0.15 policy boost
Next retrain: this mapping gets slightly higher weight
User edits something else (didn't touch ONNX correction) Same as "kept" for the ONNX-corrected word. It survived the edit.
User reverts the ONNX correction run_alias_revert_pass() detects the revert
→ penalize_mapping() -0.75
→ Delete the specific wrong alias
→ If the ONNX correction was wrong (e.g., "knot" → "AirNote" but user wanted "knot"), next retrain sees the negative → model learns to avoid this mapping
User corrects to a DIFFERENT term Original ONNX mapping penalized
New correction creates new alias + edit-policy rule
Both feed into next retrain

The key insight

The feedback loop already exists. Every correction (from any pass) goes through classify.rs when the user edits. The revert detection, policy rewards/penalties, and retrain scheduling all work pass-agnostic. ONNX corrections just need applied=true in the decision_events table to participate.

Phase 5: Compound & Dropped Word Handling ENHANCEMENT
Handle cases the ONNX model structurally can't — multi-token and missing tokens.

5a. Compound words ("air note" → "AirNote")

Already handled by edit-policy bigram rules (Pass 2). The camel_case_splits() function in proactive distortions generates the joined form ("airnote") as an STT alias and the split form ("air note") as individual tokens for edit-policy.

Enhancement: When a CamelCase term is promoted, automatically create an edit-policy rule for its space-split form. Currently this only happens if the user manually edits the split form first.

5b. Local speech drops word entirely

ONNX can't help here — no token to score. Only Local speech keyterm biasing can fix this.

Current: Only starred terms get biased.

Enhancement: Track "drop rate" per vocab term. If a term is in vocab but Local speech fails to recognize it in ≥3 consecutive dictations where the user adds it back, auto-star it for keyterm biasing. This closes the loop without biasing everything.

User rarely needs to correct again. When they do, the correction feeds back into the model.
