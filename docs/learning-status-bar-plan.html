Learning UX & Status Bar Plan

Interactive learning confirmation • Negative marking fix • Status bar as the single notification surface

1. Current Status Bar States

The status bar is a floating glass-morphism pill (300x142px window, always-on-top, all Spaces). It currently handles 6 states:

Idle
Recording
Processing
Enhancing...
Learned
EMIAC learned
Error
Recording too short

2. New Status Bar States — Learning Toasts

The status bar expands from pill → rectangular toast when the learning system needs user input. Three new toast types:

Toast A: Ambiguous Term Confirmation

When the deterministic classifier can't decide (both original and corrected are real words), expand the pill into a confirmation card:

Quick question
You changed Set → Said
Is "Said" a product, brand, or name?

Toast B: Negative Feedback Confirmation

When the system detects it's making a mistake repeatedly (user corrects a tier2 replacement back), show a removal toast:

Wrong correction detected
Said keeps changing Mac to "EMIAC" but you changed it back.
Should I stop this correction?

Toast C: Successful Learning Confirmation

When learning succeeds (deterministic, no ambiguity), show a brief confirmation with undo:

Learned
AutoNote will be recognized next time.
Retraining model... 15s

Toast D: Retrain Progress (subtle)

After learning, show retrain progress inline — no separate toast, just update the learned toast:

Training
Improving model...
Done
Model updated

When to show Toast A (ambiguous confirmation)

  1. Corrected form is a common English/Hindi word AND original is also a real word — both are valid, can't tell if it's style or STT correction. is_common_word(corrected) && !is_gibberish(original)
  2. Corrected form has mixed casing (brand signal like "Said", "Vite") but is also a dictionary word — need confirmation. mixed_case && is_dictionary_word(corrected_lower)
  3. Same word, different casing — "react" → "React". Is it the library or the verb? original_lower == corrected_lower && original != corrected

5. Negative Marking Fix — "Mac → EMIAC" Bug

  THE BUG

  1. User says "Mac" (the computer) — Local speech hears "mac"
  2. Tier2 has rule: "mac" → "EMIAC" (from earlier when user said EMIAC)
  3. Tier2 replaces: output shows "EMIAC"
  4. User corrects "EMIAC" → "Mac"
  5. classify-edit fires:
     │
     ├─ run_demotion_pass(): checks vocab terms in polish vs kept
     │  "EMIAC" in polish? YES. "EMIAC" in kept? NO → demotes EMIAC weight ✓
     │
     └─ mark_removed_feedback(): checks tier2 decision events
        Looks for rule: variant="mac", correct="EMIAC"
        But this came from STT replacements, not edit-policy!
        → penalize_rule() finds nothing → silent failure

  THE FIX

  Two changes needed:

  Fix A: Extend penalize to ALL correction sources
  ─────────────────────────────────────────────────────
  When user corrects a tier2 replacement back, penalize the
  source regardless of where it came from:
  • STT replacement alias → delete or reduce weight
  • Edit-policy rule → increment negative_count
  • Cluster-fuzzy match → no rule to penalize (transient)
  • ONNX scorer match → add to negative training data

  Fix B: Proactive detection with Toast B
  ─────────────────────────────────────────────────────
  If the user corrects the SAME replacement ≥2 times:
  • Show Toast B: "Should I stop changing Mac to EMIAC?"
  • If YES: block the rule + remove alias + retrain
  • If NO: keep the rule (user made a mistake this time)

  Fix C: Cross-source decision event logging
  ─────────────────────────────────────────────────────
  Currently tier2_decision_events only logs edit-policy and
  cluster-fuzzy. Must also log:
  • STT replacement matches (scorer_kind="stt_alias")
  • ONNX scorer matches (already logged)
  So mark_removed_feedback can find ALL applied corrections.

7. Implementation Roadmap

Phase 1: Backend — Ambiguous Classification + Confirm Endpoint

  1. Add ambiguous detection to deterministic classifier — when corrected_is_common && !original_is_gibberish, set reason = Ambiguous instead of StylePreference. classify.rs: deterministic_classify_hunks()
  2. Add ambiguous_terms field to ClassifyResponse. Each entry: {original, corrected, context, recording_id}. classify.rs: ClassifyResponse
  3. New endpoint: POST /v1/confirm-term — receives {term, action: "learn"|"skip", recording_id}. If "learn": promote to vocab, create edit-policy, retrain. If "skip": store in a skipped_pairs table so we never ask again. routes/confirm.rs (new file)

Phase 2: Backend — Negative Marking Fix

  1. Log STT replacement decisions in tier2_decision_events with scorer_kind = "stt_alias". Currently only edit-policy and cluster-fuzzy are logged. tier2.rs: apply_exact_safe result → insert event
  2. Extend mark_removed_feedback to also check stt_alias scorer_kind. When user corrects an STT alias back, delete or weight-reduce the alias. tier2_edit_policy.rs: mark_removed_feedback()
  3. Count repeated negative corrections per (variant, correct_form) pair. If count >= 2, return negative_terms in ClassifyResponse for Toast B. classify.rs: new negative_terms field
  4. New endpoint: POST /v1/block-correction — permanently blocks a correction rule and cleans up aliases. routes/confirm.rs

Phase 3: Desktop — Status Bar Toast System

  1. Add new BarState variants: confirming (Toast A), negative_confirm (Toast B), retraining (Training pill). StatusBar.tsx
  2. Listen for new events: vocab-confirm, vocab-negative, retrain-status. Each triggers the appropriate toast. StatusBar.tsx: useEffect listeners
  3. Pill → Toast animation: CSS transition from border-radius: 100px → 16px, height from 36px → 120px, with 0.25s spring easing. styles.css
  4. Button click handlers: Invoke Tauri commands confirm_term and block_correction which POST to the backend. main.rs: new Tauri commands
  5. Auto-dismiss timer: 15s for confirmations (collapses back to pill). 3s for success toasts. StatusBar.tsx: setTimeout

Phase 4: Retrain Visibility

  1. Backend emits retrain events via SSE or polling: retrain-status: {phase: "started"} when debounce fires, retrain-status: {phase: "done", duration_s} when Python finishes. classify.rs: schedule_onnx_retrain()
  2. Status bar shows training pill: Blue dot + "Improving model..." during train. Green dot + "Model updated" when done (2s auto-hide). StatusBar.tsx

8. Edge Cases Covered

  CASE 1: User ignores Toast A (15s timeout)
  → Term NOT learned, NOT permanently blocked
  → Will ask again on next correction of same pair
  → After 3 ignores of same pair → auto-classify as style_preference

  CASE 2: User clicks "Yes, learn it" on Toast A
  → Immediate vocab promotion (no 3-sighting wait)
  → Edit-policy rule created for exact variant
  → Retrain triggered
  → Toast C shows with undo (3s)

  CASE 3: Multiple corrections in one edit
  → Each ambiguous pair gets its own Toast A (queued)
  → First toast shows immediately, next after dismiss/timeout
  → Non-ambiguous corrections are learned silently

  CASE 4: "Mac" → "EMIAC" keeps happening
  → First correction: penalize the specific rule/alias
  → Second correction: show Toast B ("Stop this?")
  → User clicks "Yes, stop it": rule blocked, alias deleted
  → User clicks "It was right": negative count reset

  CASE 5: User corrects then Cmd+Z undoes
  → Edit watcher sees field revert to post_paste
  → Treated as "no edit" — nothing learned, nothing asked

  CASE 6: AX-blind app (Lark, Notion)
  → No toast shown (can't detect edits)
  → Future: passive clipboard learning may trigger toasts
