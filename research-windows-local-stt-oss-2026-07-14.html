There is no single “solved” Windows local-dictation stack.

There are, however, mature engines and a few serious desktop apps whose hard-won Windows behavior gives AirNote a concrete path. The answer is a reference stack, not a wholesale fork.

Decision

Use three references, each for a different problem.

01

Handy

Closest Rust/Tauri implementation reference. Use it for model discovery, Windows x64 Vulkan runtime packaging, backend selection, and model lifecycle.

02

OpenWhispr

Best Windows-failure-handling reference found. Its changelog and code cover bundled binaries, firewall behavior, audio device failures, local workers, and actionable recovery.

03

Sherpa-ONNX

Most mature streaming-engine reference. Use it to evaluate an ONNX/Parakeet path and learn streaming contracts—not as an automatic drop-in replacement.

The durable AirNote answer is: keep our separate-worker crash boundary, adopt Handy’s runtime packaging and device selection, learn Windows failure handling from OpenWhispr, and benchmark Sherpa-ONNX as an alternative engine. Do not fork any entire app.

Ranked reference map

What to take from each project—and what not to take.

A / DIRECT CODE REFERENCE

Handy — Rust + Tauri

Cross-platform dictation · Whisper / Parakeet / GGUF
high

Its Windows x64 setup enables dynamic CPU modules plus Vulkan, stages the runtime DLLs/modules beside the app, enumerates available devices, and gives the user Auto / CPU / GPU behavior. It also unloads models and avoids retaining two models during a switch.

Copy: backend/device discovery, runtime-package staging, load/unload semantics, and model diagnostics.

Do not copy: GPU inference inside the main app process. AirNote already has a safer worker-process pattern for GPU faults.

B / WINDOWS HARDENING REFERENCE

OpenWhispr — Electron

Global hotkey dictation · Whisper.cpp + Sherpa/Parakeet
high

Not Rust/Tauri, but unusually valuable because its Windows docs and changelog show actual field failures: binaries trapped inside Electron’s archive, Defender quarantining binaries, Bluetooth/audio-gate false silence, a local ONNX-worker crash loop, firewall prompts, and a GPU-disable escape hatch.

Copy: packaging assertions, named diagnostics, local-process fallback, Windows audio/device recovery, and installed-artifact testing.

Do not copy: Electron architecture or its localhost server design without reviewing the security trade-offs.

Repository ↗

C / ENGINE CANDIDATE

Sherpa-ONNX — C++ / ONNX

Streaming + non-streaming ASR · Windows releases
high

This is the strongest mature OSS runtime for genuinely streaming local ASR across platforms. It publishes Windows executables and supports many language bindings; OpenWhispr and TypeWhisper use it for Parakeet-class models.

Copy/evaluate: streaming recognizer contract, model metadata, release packaging, and CPU-first model options.

Do not assume: CUDA/Windows is flawless. Recent issue reports include a Windows CUDA streaming-model failure. It must pass our Hindi/Hinglish and latency test set first.

D / WINDOWS QA REFERENCE

TypeWhisper — C# / WPF

Windows-only dictation · Sherpa / whisper.cpp plugins
medium

Newer, so not a “proven with time” winner. But its source is a strong Windows product checklist: explicit AMD Vulkan vs NVIDIA CUDA handling, virtual-audio-device testing, model auto-unload, cancellation, streaming session contracts, signed installer work, and per-engine plugins.

Copy: the test matrix and lifecycle boundaries—not the whole plugin framework.

E / LONG-RUNNING LOCAL APP REFERENCE

Screenpipe — Rust + Tauri

Continuous local audio/screen capture · Whisper
high

It is not a push-to-talk typer, but it is a substantial Rust/Tauri Windows product that keeps local Whisper transcription running alongside an app for long periods. Its value is audio-device lifecycle, storage, monitoring, and operational resilience.

Copy: observability and long-running local-audio discipline. Do not copy: its broader recording/privacy architecture.

F / MATURE ENGINE REFERENCE

Buzz + whisper.cpp / faster-whisper

Desktop file transcription · Python/Qt
high

Buzz is old enough and widely used enough to be useful for Windows model/download/GPU behavior. It documents CUDA for NVIDIA and Vulkan for broader GPUs, including integrated GPUs. But it solves batch file transcription, not low-latency system-wide dictation.

Copy: installer/GPU fallback lessons. Do not copy: its batch-product architecture.

Negative evidence

Why “local Windows STT works” is not enough.

GPU availability is not GPU reliability

Whisper.cpp’s Windows Vulkan discussions include different build paths producing very different performance on an 8 GB Intel integrated-GPU machine. Sherpa-ONNX has recent Windows CUDA-streaming bug reports. A GPU selector must probe, time out, and fall back—it cannot simply check whether a GPU exists.

New dictation apps are not proof

Many Wispr Flow alternatives appeared in the last 6–12 months. Their code can offer good ideas, but their small install bases and short hardware exposure make them a watchlist, not a production foundation.

Reddit practitioner signal is consistent: Handy has positive Windows reports, but experienced users still report fragmented hardware behavior and often choose model/backend manually. Reddit and Quora are not benchmark sources; Quora was inaccessible to this research crawler, so no claims rely on it.
Recommendation for AirNote

Build a Windows ASR capability layer—not another model shortcut.

  1. Freeze current behavior. Keep Oriserve/hosted routing as the production fallback. Q4/Q8 stay clearly Experimental.
  2. Create a separate Nemotron worker. It owns probe, load, transcribe, unload, and crash reporting. It must never take down the AirNote hotkey/UI/paste process.
  3. Adopt Handy’s x64 runtime packaging. Build dynamic CPU/Vulkan modules, stage all DLLs, and verify the final installed NSIS package—not only a developer build.
  4. Add a real admission test. On first use, probe a device, load the selected model, transcribe a short bundled clip, measure latency/RAM/VRAM, then persist a pass/fail decision.
  5. Route intelligently. Auto uses the worker only after the benchmark passes; otherwise use the existing safe route. CPU Q8 must never be silently selected as “fast.”
  6. Test the actual AirNote workload. Use Hinglish, names/technical terms, 2–15 second clips, Bluetooth/WASAPI devices, 8 GB and 16 GB machines, Intel/AMD/NVIDIA GPUs, and interruption/cancel cases.
The actionable answer

Do not replace AirNote with Handy, OpenWhispr, or Sherpa.

Primary implementation baseline

AirNote’s existing process-isolated Whisper GPU worker + Handy’s Windows x64 dynamic-backend packaging and device discovery.

Primary Windows-hardening checklist

OpenWhispr’s packaged-binary verification, failure messages, audio fallback, firewall/Defender awareness, and recovery paths.

Engine experiment worth running

Sherpa-ONNX/Parakeet or its supported streaming models, tested against the exact AirNote Hinglish dictation corpus before any product switch.

Things to reject

A pure CPU 600M model as default, “GPU exists” as the only eligibility check, and a direct in-process Vulkan integration that can crash the app.
