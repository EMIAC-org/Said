Meeting Lifecycle & Edge Cases

Every step from meeting creation to Lark sync, including disconnects, late joiners, role enforcement, and the slot-based AI pipeline.

1 · Role System (Soft RBAC from Lark)

Roles are imported from Lark during directory sync. No hard-coded RBAC — everything is configurable per org. When Slack or another connector is added later, the same string-based role field is reused.

Lark Roles

tenant_manager → synced from Lark admin API

department_manager → per-department lead

member → default for all synced users

→
Said Roles

COMPANY_ADMIN → full org control, all permissions

MANAGER → create meetings, manage participants

MEMBER → join meetings, view history

Per-Org Configuration

Each org has a meeting_creator_roles setting (default: ["COMPANY_ADMIN", "MANAGER"]). The org admin can widen this to include MEMBER if they want everyone to create meetings. Stored as a JSON array on the orgs table — no code change needed to update.

2 · Meeting Discovery — How the Desktop App Knows
1

User opens "Meetings" section

The Sidebar has a "Meetings" nav item (clock icon). When clicked, the app checks if it's connected to an enterprise server (checks localStorage for said:enterprise JWT). If not connected, shows "Connect to Enterprise" prompt.

2

App polls the server

Once connected, the Meetings page calls GET /v1/meetings?status=scheduled,live every 10 seconds. Returns all meetings where the user is a participant. No persistent WebSocket needed for discovery — simple polling, battery-friendly.

3

Meeting appears as invitation card

Each meeting shows: title, participant avatars, status (scheduled / live / how long it's been running). Live meetings have a pulsing red dot. The "Join" button only appears for live meetings. Scheduled meetings show "Waiting for host to start."

4

User clicks "Join"

App connects to wss://server/v1/meetings/:id/ws?token=.... Receives a connected message. Enters meeting mode: continuous audio capture starts (no hotkey needed), transcript chunks stream to server. The title bar shows a red recording indicator.

5

Meeting ends

Host (or admin) clicks "End Meeting" on dashboard or app. Server sets status to ended, disconnects all WebSocket participants, broadcasts meeting_ended. Desktop apps exit meeting mode automatically. Final AI processing runs on the last slot.

3 · Slot-Based AI Pipeline

The meeting transcript is divided into slots — natural intervals of 1-5 minutes. Each slot is an atomic AI processing unit. The AI receives the previous summary + the new slot's chunks, and produces an updated summary, new tasks, and decisions.

Slot Boundary Rules

Natural pause: All speakers silent >3 seconds AND at least 60s since last slot boundary.

Max cap: 5 minutes elapsed since last slot — force-close at the next sentence end, even if someone is still talking.

Whichever triggers first closes the slot.

AI Processing Per Slot

Input: previous summary + all chunks in this slot (speaker-tagged, ordered by timestamp).

Output: updated summary, new action items (with assignee detection), new decisions.

Async: processing happens in background — doesn't block the live transcript stream. Results pushed via WebSocket when ready.

Slot Data Model

meeting_slots
├── id              UUID
├── meeting_id      UUID (FK → meetings)
├── slot_index      INT  (0, 1, 2, ...)
├── start_ms        BIGINT
├── end_ms          BIGINT (NULL while open)
├── chunk_count     INT
├── word_count      INT
├── speaker_ids     UUID[] (who spoke in this slot)
├── ai_status       TEXT (pending | processing | done | failed)
├── summary_delta   TEXT (what AI produced for this slot)
├── tasks_detected  INT
├── decisions_detected INT
└── created_at      TIMESTAMPTZ
4 · Late Joiner Catchup

When someone joins a meeting that's already in progress, they need full context without downloading the entire transcript history. The server sends a catchup packet immediately after the WebSocket connected message.

Catchup Packet Contents

1. Latest AI Summary

Covers all processed slots. If 10 minutes have passed, this is a concise summary of everything discussed so far.

2. Current Slot Chunks

Raw transcript from the current (unprocessed) slot only. This is what's happened since the last AI run — usually <2 minutes of text.

3. Participant State

Who's in the meeting, when they joined, who's currently speaking. Plus all detected tasks and decisions so far.

Example: Priya joins 8 minutes late

0:00
Meeting starts

Abhishek, Anish, Rahul join. Slot 0 begins.

2:15
Slot 0 closes (natural pause)

AI processes: generates summary_v0, detects 1 task.

4:30
Slot 1 closes (natural pause)

AI processes: summary_v1 (builds on v0), detects 2 more tasks, 1 decision.

5:00
Slot 2 opens

Abhishek starts discussing WebSocket architecture. Chunks streaming.

8:00
Priya joins → Catchup sent

Summary: summary_v1 (covers 0:00–4:30)
Current slot chunks: 12 chunks from Slot 2 (5:00–8:00)
Tasks so far: 3 tasks with assignees
Decision: "Plain WebSocket, not Socket.IO"
Participants: Abhishek (0:00), Anish (0:00), Rahul (0:00)

Priya has full context in ~2KB of data instead of the full 8-minute transcript.

5 · Disconnect Recovery

Client-Side (Desktop App)

1. WebSocket drops (network issue, sleep, etc.)

2. App continues recording audio locally — buffers transcript chunks in memory with sequential chunk_index

3. Auto-reconnect with exponential backoff (1s → 2s → 4s → 8s → max 30s)

4. On reconnect, sends {"type": "resume", "last_chunk_index": N}

5. Flushes all buffered chunks to server in order

Server-Side

1. Detects client disconnect (WebSocket close/timeout)

2. Marks participant status as disconnected (not left — they didn't choose to leave)

3. On reconnect with resume, checks last stored chunk_index for this speaker

4. If gap detected (e.g., chunks 48-52 missing), marks a gap in the slot metadata

5. AI prompt includes: "Note: ~30s gap in Speaker X's transcript due to connection loss"

Participant Status Machine

invited → joined → disconnected → joined (reconnect) → left (voluntary or meeting ended)
